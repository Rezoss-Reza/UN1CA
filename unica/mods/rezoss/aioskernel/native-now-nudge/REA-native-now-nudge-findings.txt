Traced reply path and session behavior
-------------------------------------
1. Existing patch 0026 intercepts SmartReplyResolver.execute with InAppReplies.start.
   InAppReplies.screen also consumes parsed conversation messages. These go to
   RezossAI -> QwenEngine -> io.mesalabs.rezoss.qwen.EngineService.
2. The original SrPromptProcessor.textPrompting uses text and target_language,
   optional records/date, and SmartReplyCategory.CONTEXTUAL for V3. V2 uses LONG.
   This is not an image-to-text request. The SmolVLM vision proof is unrelated
   to running this original Samsung contextual-reply model.
3. SCS SmartReplyServiceExecutor targets package com.samsung.android.intellivoiceservice
   with action android.intellivoiceservice.SmartReplyService.
4. Installed Language Core has the qc_sm8850.s26 contextual-reply handler, which
   constructs the Samsung language/records prompt. Its AIOS connector binds an
   AIOSKernelServiceContext, creates AIOSTaskPipeline from ModelInfo/AdapterInfo,
   and preloads the model. Only status 0 counts as successful preload.
5. prepareModelPipeline sets LoRA task and language and calls preLoadModel.
   unloadModel calls unLoadModel and clears modelLoaded on success. SrPromptProcessor
   close releases SmartReplyer. Optional prewarm calls Configuration.prewarmLlm
   for contextual_reply only if the feature gate is enabled and >=3 GiB is available.

This is static client/connector evidence, not an end-to-end observed native
reply. SamsungIntelliVoiceServices internals were not fully decompiled here.
The incompatible model prevents a valid end-to-end native acceptance test.

touches its InAppReplies and NotificationReplies interception boundary; it does
